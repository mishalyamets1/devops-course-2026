# Git vs SVN: сравнение

## 1. Почему в Git ветвление «дешёвое», а в SVN — «дорогое»?

### Git

Git — **распределённая** система контроля версий. Каждый разработчик хранит у себя полную копию репозитория со всей историей.

- **Ветка — это просто указатель** (ref) на конкретный коммит. Создание ветки — это запись одной строки в `.git/refs/heads/`, без копирования файлов и без обращения к серверу.
- Переключение между ветками (`git checkout` / `git switch`) — **локальная операция**, выполняется за миллисекунды.
- Слияние веток хорошо поддерживается: трёхстороннее слияние, rebase, стратегии разрешения конфликтов.
- Можно создавать десятки веток «на каждую фичу» без каких-либо накладных расходов.

### SVN

SVN — **централизованная** система. Репозиторий живёт на сервере, у разработчика есть только рабочая копия (working copy).

- Ветка создаётся через **`svn copy`** — копирование каталога внутри репозитория на сервере. Это не «указатель», а **новый путь** (`/branches/feature-x`), который со временем накапливает свою историю.
- Переключение на другую ветку — это **`svn switch`**: смена URL рабочей копии и синхронизация с сервером. Операция заметно тяжелее, чем в Git.
- Слияние в SVN исторически было болезненным: нужно отслеживать `mergeinfo`, понимать, какие ревизии уже были слиты, использовать `svn merge --reintegrate`. С SVN 1.5+ ситуация улучшилась, но ментальная и операционная нагрузка выше.
- Из-за централизованной модели каждое значимое действие с веткой (создание, переключение, слияние) **требует взаимодействия с сервером** и более тщательного планирования.

**Итог:** в Git ветка — лёгкий локальный указатель; в SVN — отдельная «копия» пути в центральном хранилище с более тяжёлым жизненным циклом.

## 2. Можно ли в SVN сделать коммит без интернета? Почему?

**Нет, полноценный коммит в SVN без связи с сервером сделать нельзя.**

Причина в архитектуре:

- SVN хранит **историю только на сервере**. Локально у вас — рабочая копия файлов и метаданные (`.svn`), но не полноценный репозиторий.
- Команда `svn commit` **отправляет изменения на сервер** и создаёт новую ревизию в центральном хранилище. Без сетевого соединения с сервером коммит завершится ошибкой.
- Без интернета в SVN можно:
  - редактировать файлы;
  - делать `svn diff` локально;
  - накапливать изменения в рабочей копии.
- Но **зафиксировать** (commit) их в истории проекта — только при доступности сервера.

Для сравнения: в Git `git commit` записывает снимок **локально**, интернет нужен только для `git push`.

## 3. В каких сценариях SVN до сих пор может быть предпочтительнее Git?

SVN не «устарел полностью» — в ряде ситуаций он остаётся разумным выбором:

| Сценарий | Почему SVN |
|---|---|
| **Жёсткий централизованный контроль** | Один сервер — единая точка аудита, политик и резервного копирования. Удобно для регулируемых отраслей (банки, госсектор). |
| **Права доступа на уровне каталогов** | SVN из коробки поддерживает **path-based authorization**: разным командам — доступ только к «своим» папкам в одном репозитории. В Git права обычно бинарные (весь репо или ничего), если не использовать монорепо-инструменты. |
| **Частичная выгрузка (sparse checkout)** | Долгое время SVN позволял checkout только нужных подкаталогов большого монорепозитория — удобно при медленных каналах и огромных деревьях. |
| **Legacy-инфраструктура** | Компания уже инвестировала в SVN (хуки, CI, интеграции с Jira/Bamboo/CruiseControl, обучение сотрудников). Миграция на Git — дорогой проект. |
| **Простой линейный workflow** | Команда из 5–10 человек, trunk-based development, без feature-веток — SVN с TortoiseSVN может быть проще для не-разработчиков (техписатели, дизайнеры). |
| **Большие бинарные файлы (legacy)** | Для CAD, игровых ассетов, медиа SVN historically использовался с locking (`svn lock`). Git LFS решает проблему, но не везде внедрён. |
| **Windows/.NET-экосистема** | VisualSVN, AnkhSVN, интеграция с Visual Studio — привычный стек для корпоративной .NET-разработки. |

**Когда Git почти всегда лучше:** распределённая команда, активное ветвление, code review через pull request, open source, CI/CD с feature-ветками, офлайн-работа.

**Когда SVN может быть лучше:** централизованная организация, строгий контроль доступа по папкам, legacy-процессы и инфраструктура, минимальное ветвление.
